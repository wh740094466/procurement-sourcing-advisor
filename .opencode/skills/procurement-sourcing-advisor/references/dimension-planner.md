# 评比维度规划（Stage 0）

维度不是套模板，而是从**使用需求**推导出来的。规划顺序固定为四步，每一步都要能写进确认单让用户核对。

## 第一步：场景 → 需求

| 使用诉求 | 应成为需求/维度 | 判定字段 |
|---|---|---|
| 7×24 连续运行 | 保修年限、企业级定位、散热/噪音 | `detail.warranty`、`title`、`reviews` |
| 静音环境 | 噪音、评价中的噪音主题 | `attributes.noise_db`、`reviews` |
| 移动/差旅 | 重量、续航、接口 | `attributes.weight_kg`、`attributes.battery` |
| 多人共用 | 耐用性、售后响应、负评率 | `title`、`reviews` |
| 数据安全 | CMR、MTBF、RAID 兼容 | `attributes.recording`、`attributes.mtbf` |
| 预算刚性 | 价格只进 value，不设高权重 | `price` / 锚点 |

场景写进 `brief.usage_profile`，不要只写一句 `usage_context`。

## 第二步：需求分层

- `must`：不满足就不能用（容量、接口、合规、发票）
- `should`：满足度可比较，带权重（保修年限、定位、噪音、重量）
- `value`：同价位比的性能（规格档次、缓存、刷新率）
- `risk`：渠道、评价，只影响置信度与提示

一条需求只能落在一层；`should` 必须有 weight，且组内权重和为 1。

## 第三步：落到可判定字段

每条需求/维度必须写清楚 `field` 与 `op`：

```json
{"id": "warranty5", "type": "should", "label": "5 年保修", "weight": 0.5,
 "field": "detail.warranty", "op": "contains_any", "value": ["5年", "五年"], "missing": "worst"}
```

落不到字段的（做工、手感）只能进 `manual`，且必须要求证据文本，不能伪装成硬条件。

## 第四步：定权重与阈值

- 组内权重和为 1，取 0.05 的倍数
- `fit_threshold` 默认 0.8：低于它就是“需求未完全满足”，不参与推荐
- 价格不设独立权重：它只作为 `value = 性能 / 价格指数` 的分母
- 任一维度权重不超过组内 0.6，避免单指标决定结果

## 常见品类的起手式

| 品类 | must | should（fit） | value | risk |
|---|---|---|---|---|
| 企业级硬盘 | 容量、接口、CMR、发票、≥3 年保修 | 5 年保修、企业级定位、全新 | 定位档次、缓存 | 渠道、评价 |
| 办公显示器 | 尺寸、分辨率、发票 | 面板、支架、保修 | 刷新率、色域 | 渠道、评价 |
| 轻薄本 | 内存、硬盘、发票 | 保修、重量、续航 | CPU 档位、屏幕 | 渠道、评价 |
| 办公椅 | 承重、发票 | 腰托、调节、保修 | 网布/材质、认证 | 渠道、评价 |

模板只用于起手，实际权重必须按这次的使用场景调整，并写进 `rationale`。

## 确认单检查项

- [ ] 每条 `must` 都能在页面上判定
- [ ] 每条 `should` 都有权重和字段
- [ ] `value` 至少一个维度，且不是价格的重复
- [ ] `risk` 不参与主排序
- [ ] 阈值、权重、假设都出现在确认单里
- [ ] 用户确认后才冻结
